# 02 · 技术选型

## 1. 选型结论

| 层 | 选型 | 说明 |
|---|---|---|
| 引擎 / 渲染 | **Godot 4.7（.NET 版）** | 只用它的渲染、输入、界面和着色器；**不用**它的物理引擎和高层多人 API |
| 语言 | **C# 12，.NET 8** | 客户端、服务器、测试共用同一份玩法代码 |
| 玩法仿真 | 自研 `Tank.Sim`：纯 C# 类库，不依赖引擎和网络 | **30 Hz 固定步长、`float` 运算**（`System.Numerics`、`MathF`），米、秒、弧度，Y 轴向上；贴地运动学 + 有向矩形（OBB）碰撞 + 解析弹道 |
| 网络传输 | **LiteNetLib 2.x**（UDP） | 用两种投递方式：不可靠（输入、快照）和可靠有序（事件、房间、开局）；未连接消息做局域网广播发现 |
| 同步模型 | **权威服务器 + 状态同步 + 客户端预测 + 插值** | 每个客户端只收到自己看得见的东西；详见 [03](03-netcode.md) |
| 序列化 | 自研位流（`BitWriter` / `BitReader`）+ 按客户端的增量快照 | 包小、热路径不分配内存，协议完全自己控制 |
| 专用服务器 | .NET 控制台程序 `Tank.Server`（无头，**不依赖 Godot**） | 开房的玩家在客户端进程里用独立线程跑同一个服务器 |
| 美术 | 代码程序化生成网格（`Art/Mesh`），卡通着色器 | 不用外部模型和贴图；唯一的外部素材是界面字体 |
| 在线升级 | `Tank.Update`：签名清单 + 整包替换 | 见根目录 README |
| 测试 | xUnit；Coverlet 收集覆盖率；自研网络压测 `Tank.Soak` | 见 [04 §5](04-architecture-and-plan.md#5-测试) |
| CI | GitHub Actions：单元测试、soak、编译服务器和客户端；发布工作流打包 macOS 客户端和 macOS 服务器（只支持 macOS） | |

> 锁定的版本：Godot 4.7.2 .NET 版（`Tank.Client.csproj` 的 `Godot.NET.Sdk/4.7.2`）、.NET SDK 8.0.425（`global.json`，`rollForward: latestFeature`：可用更高的 8.0 SDK）、LiteNetLib 2.1.4、xUnit 2.9.3（`Directory.Packages.props`）。

## 2. 为什么是 Godot + C#

1. **3D 需求不重**：一张 400 m 的地图、十来辆车、几百丛草，Godot 4 足够，不需要 Unreal 那样的引擎。
2. **玩法必须和引擎解耦**：客户端预测要能“把自己的车倒回服务器给的状态，再重放几十个 tick”。引擎物理做不到可控的重放，所以仿真是自己写的纯代码。C# 库同时被 Godot 客户端和无头服务器引用，在 xUnit 里不开引擎就能测。
3. **场景和资源是文本**：`.tscn`、`.gdshader` 都是纯文本，git diff 友好，AI 工具也能直接读写。
4. **免费、MIT 协议、包小**：没有授权费，桌面导出包几十 MB。
5. **C# 比 GDScript 适合写网络和仿真**：静态类型、`struct` 和 `Span<T>` 能做到零分配，单测生态成熟，性能更好。

## 3. 为什么不用 Godot 自带的 MultiplayerAPI

| 维度 | Godot MultiplayerSynchronizer / RPC | LiteNetLib + 自研同步 |
|---|---|---|
| 客户端预测和对账 | 没有，要自己写 | 自己写（反正都要写） |
| 增量快照 | 没有 | 自己控制 |
| 按可见性给每个人发不同的数据 | 很难（同步器面向“所有人看同一份”） | 每个客户端单独建快照，天然支持 |
| 能否在无引擎的服务器里跑 | 要 Godot 无头模式 | 纯 .NET 就能跑 |
| 局域网发现 | 要自己用 PacketPeerUDP 实现 | 内置广播和未连接消息 |
| 单元测试 | 依赖引擎 | 纯 C#，进程内同时起服务器和客户端，或用内存回环网络 |

Godot 的高层多人 API 适合回合制和休闲游戏，做不出射击游戏要的手感，也做不了“没被点亮的敌人不下发”。所以 Godot 只当渲染层。

## 4. 备选方案对比

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| **Godot 4 + C# + LiteNetLib** | 轻量、免费、文本资源、代码全掌控 | 网络同步要自研（[03](03-netcode.md) 已实现） | ✅ **采用** |
| Unity 6 + Netcode for Entities | 自带预测、插值和延迟补偿 | 依赖 DOTS / ECS，学习曲线陡；场景文件不便文本协作；授权政策有风险 | 次选 |
| Unity + FishNet / Mirror | 生态丰富、教程多 | 预测功能各家不一，深度定制仍要改源码 | 不采用 |
| Unreal 5 | 网络复制成熟、画质顶级 | 对这个规模严重过重：C++ 编译慢、包大、上手成本高 | 不采用 |
| Web（Three.js + TypeScript + WebRTC） | 免安装 | 浏览器不能 UDP 广播，局域网发现要另起信令服务器；GC 和后台标签页节流会卡 | 不采用 |
| Bevy（Rust）+ lightyear | 性能好、ECS、自带预测和回滚 | 生态不稳定，没有编辑器 | 不采用 |

## 5. 仿真：30 Hz、浮点、自己写物理

| 决策 | 选择 | 理由 |
|---|---|---|
| 频率 | **30 Hz** | 坦克节奏慢，30 Hz 足够；点亮计算和带宽都比 60 Hz 少一半；画面靠插值，在高刷屏上照样平滑 |
| 数值 | `float` + `MathF` | 不做锁步，不要求各平台逐位一致；客户端的微小偏差由对账修正 |
| 物理 | 贴地运动学 + OBB 碰撞 + 解析弹道 | 引擎物理不确定，预测和对账会一直打架；客户端也不用 Godot 物理，碎片、飞起的炮塔都是按曲线算的纯表现 |
| 随机数 | 种子化 XorShift；射击的种子由 `(tick, 车号, 第几发)` 推出 | 客户端能预测出和服务器一样的散布 |
| 地图 | 服务器生成后把高度（1 cm 精度）和物件表整个发给客户端 | 不同 CPU（Apple 芯片和 Intel 的 Mac）上 `MathF` 可能有末位差别；地图生成里一处判断不同，物件编号就全对不上了 |

`Tank.Sim` 不许引用引擎和网络库，不许用系统时间和 `System.Random`；`tests/Tank.Sim.Tests/ArchitectureTests.cs` 按程序集引用和字段类型（没有 `Random`/`DateTime`/`Stopwatch` 字段）检查。

## 6. 同步模型：状态同步，不用锁步或回滚

| | 权威服务器状态同步（**采用**） | 确定性锁步 / 回滚（GGPO 式） |
|---|---|---|
| 代表作 | CS、Quake、坦克世界、Overwatch | 格斗游戏、RTS |
| 自己的操作 | 预测后零延迟 | 回滚后零延迟 |
| 别人的表现 | 插值，平滑但落后约 100 ms | 预测 + 回滚，人多时容易抖动、穿帮 |
| 确定性要求 | 只要求自己的车能重放（部分确定即可） | **所有平台逐位一致**，浮点仿真做不到 |
| 视野保密 | 服务器只发看得见的敌人 | 每个客户端都有全部状态，点亮形同虚设 |
| 中途加入和断线重连 | 发一份开局数据和完整快照即可 | 要追帧，复杂 |
| 10 人的扩展性 | 好 | 回滚成本随人数上升 |

**结论**：状态同步。浮点仿真本来就做不到跨平台逐位一致，锁步和回滚都不可行；点亮玩法也要求服务器只给每个人发他能看到的东西。

**不做延迟补偿（回溯）**：炮弹有飞行时间（穿甲弹初速 720～850 m/s，飞 200 m 要 0.24～0.28 秒，高爆弹更慢），远大于局域网的往返延迟（有线 1 ms 以内），所以命中判定直接用服务器当前状态，不把目标倒回射手看到的位置。开炮的位置和朝向取射手在那个输入 tick 的权威状态。
